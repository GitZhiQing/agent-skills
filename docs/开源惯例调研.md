## 摘要

本仓库的**单 skill 层已经相当规范**：SKILL.md frontmatter（name == 目录名、三段式 description、metadata.version）与官方 Agent Skills 开放规范一致，MIT 许可也是社区主流。**不规范感主要来自仓库级**：① 缺少社区标准分发通道（`.claude-plugin/marketplace.json`、可被 `npx skills add` 发现的目录布局），外部用户无法一键安装；② 多 skill 仓库的社区惯例是把 skills 收进 `skills/` 子目录，本仓库是根级平铺；③ README 缺「外部用户从零安装」的 30 秒路径。好消息是：`marketplace.json` 的 plugin 条目支持显式路径，**不重构目录也能接入两条标准通道**。

## 1. 生态背景：skills 已是开放标准

Agent Skills 由 Anthropic 设计并作为开放标准发布（SKILL.md + YAML frontmatter），约 90 天内被 OpenAI、Microsoft、Google 等采纳 [S14]。规范由 [agentskills.io](https://agentskills.io) 维护，提供 `skills-ref validate` 校验工具 [S1]。围绕它形成了三层分发生态：

1. **Claude Code plugin marketplace**（官方机制）：仓库根放 `.claude-plugin/marketplace.json`，用户 `/plugin marketplace add owner/repo` 一键安装，版本随 `plugin.json` 的 version 字段更新 [S5][S8]。
2. **skills.sh CLI**（Vercel 运营的 Agent Skills Directory）：`npx skills add owner/repo/skill-name`，支持 20 个 agent 平台，装到 `~/<agent>/skills/` 或项目 `./<agent>/skills/`，推荐 symlink 方式（与本仓库 `skills-link.sh` 的 junction 思路同构）[S3][S6]。
3. **手动 clone/copy**：把 skill 目录放进 agent 的 skills 目录 [S6]。

## 3. 本仓库已符合的惯例

- **frontmatter 规范** [S1]：`name` 全小写连字符且 == 目录名 ✓；三段式 `description`（做什么 + 何时用 + 触发词）正是官方 good example 的写法 ✓；`metadata.version` 与官方规范示例完全一致 ✓（社区并无统一版本机制，个人集合用台账跟随是合理变体 [S4][S7]）。
- **许可** [S2][S4][S7]：MIT 是个人/社区集合主流（官方用 Apache-2.0），根 LICENSE + skill 内副本的做法稳妥 ✓。
- **多 skill 一仓库** [S3]：`owner/skills` 的仓库名与内容形态正是 skills.sh 索引的典型形态 ✓。
- **本机分发思路** [S6]：junction/symlink 单一来源恰是 `npx skills add` 推荐的安装方式，方向正确，只是没包装成他人可用的通道。
- **治理脚本化**：lint/doctor/new 脚手架在社区仓库中少见（superpowers 有 evals + tests，多数仓库没有），属于超出平均水平的部分 ✓。

## 4. 缺口清单（按影响排序）

1. **缺标准分发通道（最关键）**。没有 `.claude-plugin/marketplace.json`，Claude Code 用户不能 `/plugin marketplace add GitZhiQing/skills`；skill 在根级平铺、不在 `skills/` 下，`npx skills add` 只能靠递归兜底发现 [S5][S6]。「开源了但社区装不了」正是「不规范感」的主因。
2. **目录布局偏离惯例** [S2][S4][S7]：社区多 skill 仓库一律 `skills/<name>/`。但重构成本高（junction 脚本、lint、台账全要动），且 `marketplace.json` 的 plugin 条目支持 `skills` 字段显式指定路径——**可平铺接入 marketplace；skills CLI 也兼容读 marketplace 清单 [S6]**。建议不改目录，用清单兼容，并在设计文档记录该决策。
3. **README 缺外部安装路径** [S7]：安装节只写了「本机已链接三端」的口径。社区标配是 clone 后 30 秒三步（本仓库实际就是 `git clone → bash scripts/skills-link.sh --all`，能力已具备，只是没按外部用户视角写）。
4. **frontmatter 缺 `license` 字段** [S1]：官方可选字段，社区常见。逐 skill 加 `license: MIT` 成本一行。
5. **`ddgs-web-access` 缺 `compatibility` 字段** [S1]：官方明确「有环境要求就该写」（需 uv ≥ 0.5、联网装依赖）。
6. **无可执行代码的免责/安全说明** [S2][S12]：官方仓库保留 Disclaimer 节；skill 携带可执行脚本属供应链攻击面，社区安全厂商已演示恶意 skill 的利用路径。本仓库 README 许可节可加一句「含可执行代码，安装前请审阅 bin/ 与 scripts/」。
7. **（可选）语言**：一手生态全英文，全中文 README 会显著降低可发现性 [S3]；非规范问题，视目标受众决定是否加英文简介。

## 5. 建议动作（低成本 → 高成本）

1. README 补「从 GitHub 安装」三步（clone → `skills-link.sh --all` → 各 agent 触发验证），并把许可节补免责句。
2. 三个 skill 的 frontmatter 补 `license: MIT`；ddgs-web-access 补 `compatibility`。
3. 新增 `.claude-plugin/marketplace.json`（plugin 条目用显式路径指向三个平铺 skill），`claude plugin validate .` 验证后即接入 Claude Code marketplace 通道，skills CLI 通道也随之兼容 [S5][S6]。
4. 用官方 `skills-ref validate` 跑一遍三 skill，作为 skills-lint 的补充（可挂进 lint）[S1]。
5. 是否把 skills 迁入 `skills/` 子目录：建议**暂缓**，先观察 marketplace 通道效果；若迁移，按 skills-new 脚手架 + lint + 台账同步一次完成。

## 6. 批评与风险视角（多样性自检）

- 生态「理论上收敛、实践中碎片化」：同一 skill 跨 agent（Claude Code / Codex / Cursor…）安装路径各异，维护多 harness 适配是真实负担 [S10][S4]。
- 社区存在「skills ≈ AGENTS.md + 链接文件」的重复性质疑 [S13]；OSS Insight 甚至用数据论证 skills 可能是过渡形态而非终局 [S11]——不影响本仓库自用价值，但开源定位上不宜押注单一生态叙事。
- 供应链安全：skill 的动态上下文可先于模型层防御执行命令（Datadog 演示）[S12]。本仓库含 bash/Python 可执行代码，发布免责与「审阅后安装」提示是社区认可的最低动作 [S2]。

## 7. 局限与未覆盖

- 搜索轮数 4 次，低于 high 档 8~15：主题为文档型生态，一手页面（规范、官方文档、标杆仓库）定向抓取的收益高于增量搜索，登记来源 22 条（在用 14）符合档位要求。
- platform.claude.com 的《Skill 编写最佳实践》仅经检索摘要引用，未逐条抓取；其要点（description 写法、SKILL.md 长度）已由 agentskills.io 规范覆盖 [S1][S9]。
- 未覆盖：skills.sh 的收录/排序算法细节（是否自动索引所有 GitHub 公开仓库未获官方明说 [S3][S6]）；中文独立社区（非翻译/解读性质）的一手实践未找到代表性来源。
- 观点标注：§6 全部为社区观点/分析，非事实结论；表格中 stars 等数据为抓取时点值，快速变化。
