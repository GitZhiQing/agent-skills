## 1. 背景与目标

### 1.1 背景

工作区常混杂多轮、多主题的变更。一次性全量提交会让历史难以回溯、回滚与 bisect；只按文件类型拆分又会把同一逻辑变更切碎。2026-10-19 本仓库把提交规范固化为 `docs/开发与维护规范.md` §10：`type(scope): 摘要` + 列表式 body；theme-commit 原 0.1.1 只生成一句话摘要，已与项目规范脱节。

### 1.2 目标

把 theme-commit 从"分组 + 提交"升级为**可审计的提交流程**：

- 提交前看清 staged / unstaged / untracked 与进行中操作；
- 先给主题计划，用户确认后再落盘；
- 每个提交只承载一个逻辑主题，消息符合项目规范；
- 提交前做快速检查，提交后核对文件集合与消息；
- 不推送、不改写已发布历史；失败时保留现场并报告。

### 1.3 非目标

| # | 不做 | 理由 |
| --- | --- | --- |
| NG-1 | 不推送 / 不建 PR / 不合并 | 推送与 PR 是独立的高风险步骤，应有单独确认 |
| NG-2 | 不 amend / rebase / reset / force push | 不改写已发布历史；错误提交交由用户决定 |
| NG-3 | 不做 hunk 级拆分 | 项目 §10 明确不做；`git add -p` 是交互式命令，纯提示词 agent 不可靠 |
| NG-4 | 不替代 commitlint / hook / CI | 纯提示词只能建议；可靠拦截依赖项目工具链 |
| NG-5 | 不做通用 git 客户端 | 只覆盖"按主题提交"这一件事 |

## 2. 现状差距（0.1.1）

| 维度 | 0.1.1 | 影响 |
| --- | --- | --- |
| 消息格式 | 一句话摘要 | 与 §10 的 type/scope/body 冲突；可能被 commit-msg hook 拒绝 |
| staged 状态 | 只看 `git status` / `git diff` | 已有暂存改动会被静默混入首个提交 |
| 暂存方式 | `git add <file>` 但无显式路径约束 | 易误用 `git add -A`；无法保证提交边界 |
| 空提交 | 无守卫 | 主题为空时提交失败或产生空提交 |
| 检查 | 无 lint / 测试 / diff-check | 可能提交红状态，破坏 bisect |
| 安全 | 无敏感 / 大文件 / 生成物检查 | 可能提交 `.env`、密钥、构建产物 |
| hook | 未提及 | hook 失败时可能误用 `--no-verify` |
| 收尾 | 只 `git status` | 无法发现"工作区干净但提交夹带错误文件" |
| 失败恢复 | 未定义 | 批次中途失败后状态不明 |
| 测试 | 4 个快乐路径场景 | 未覆盖 staged、空提交、hook、检查失败等 |

## 3. 设计决策

### D1 对齐项目 §10 / Conventional Commits

消息格式、type/scope 词表、subject 长度与 body 列表以项目规范为准；项目没有规范时使用本 skill 的默认格式。subject 采用项目 §10 的 ≤50 字，不套用社区 72 列硬换行；body 用列表优先保证 Markdown / 终端可读性。这样本仓库与通用项目都能用。

### D2 默认计划预览 + 结构化提问确认

主题分组错误或消息错误在"不改写历史"的边界下修复成本高。默认先给紧凑计划（主题 / 文件 / 消息 / 检查），再调用宿主可用的结构化提问 / 选择工具（AskUserQuestion、request_user_input、elicitation 等，以实际可用为准）询问是否提交；宿主没有该工具时退回纯文本提问。选项含确认提交 / 调整计划 / 取消。用户明确说"直接提交"时跳过预览与提问。一次计划只问一次，不逐提交重复询问。

### D3 快速检查 + 批次完整测试

每个提交前跑与改动相关的快速 lint / format / `git diff --cached --check`；全部提交后跑一次项目完整测试 / 构建。兼顾"每个提交尽量可构建"与多提交场景的耗时。

### D4 不做 hunk 级拆分

项目 §10 明确不做；`git add -p` / `git add -e` 依赖交互式编辑器，纯提示词 agent 无法可靠完成。单文件多主题时整文件归主主题，body 列出次要改动；用户要求更高纯度时请其手动拆分或调整实现顺序。

### D5 显式暂存，禁止 `git add -A`

只 stage 计划中列出的路径；删除 / 重命名显式列出。参考 agent 提交工作流的通行做法：`git status --short` → 显式 `git add <paths>` → `git diff --cached --stat` 复核。

### D6 不推送、不改写历史

提交后的推送、PR、发布是独立步骤。skill 不 amend / rebase / reset / force push；发现错误提交时报告，由用户决定。

### D7 安全预检是最佳努力

敏感文件名、>5MB / >50MB 文件、生成物、ignored 文件做提示级检查；纯提示词无法保证拦截。项目应配置 secret scanning、pre-commit、CI 兜底。

### D8 失败保留现场

检查 / hook / 提交失败时停止，报告已成功提交、剩余主题、index / worktree 状态；不自动 `reset --hard` 或 amend。用户可据此续跑或人工修复。

### D9 渐进披露拆分（v0.3.0）

完整提交信息规范移入 `references/提交信息规范.md`，失败处理表移入 `references/失败处理.md`；SKILL.md 保留四步主流程与摘要式规范。理由：提交主路径每次都要，footer / `BREAKING CHANGE` 与异常处理表只在特定场景读取。语义不变，升次位版本。

## 4. 需求规格

### 4.1 功能需求

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-1 | **预检**：确认仓库根、分支、进行中操作、staged / unstaged / untracked、最近提交风格 | 合并 / 变基 / cherry-pick / 冲突 / detached HEAD 时停止；无变更时报告并停止 |
| FR-2 | **staged 隔离**：已有暂存改动不静默混入 | 列出 staged 文件并询问纳入 / 用户处理 / 经同意后 unstage |
| FR-3 | **主题分组**：测试随功能、格式化 / 重构尽量独立、依赖锁文件随依赖或单独提交 | 每个提交的文件属于同一逻辑主题；共享文件在 body 说明 |
| FR-4 | **计划预览与确认**：主题 + type(scope) + body + 文件 + 检查项；计划后通过宿主结构化提问工具询问是否提交 | 默认等待确认；无结构化提问工具时退回纯文本，选项含确认 / 调整 / 取消；用户说"直接提交"可跳过；调整后按新计划执行；不逐提交重复询问 |
| FR-5 | **消息规范**：`type(scope): 摘要` + 列表式 body | subject ≤50 字、无版本号、无句号；body 每条一个变更；版本写 body，并按项目规则同步 pyproject / plugin / marketplace / 台账 |
| FR-6 | **显式暂存与空提交守卫** | 只 `git add -- <路径>`；`git diff --cached --quiet` 命中时跳过 |
| FR-7 | **检查**：快速检查 + 批次完整测试 | 快速检查失败停止；完整测试在全部提交后运行一次，失败则报告且不改写历史 |
| FR-8 | **hook**：不绕过、失败停止、修改文件后重新暂存 | 不出现 `--no-verify`；hook 失败有报告 |
| FR-9 | **安全预检**：敏感 / 大文件 / 生成物 / ignored 文件 | 命中时先询问或拒绝；不强行提交 |
| FR-10 | **提交后验证** | `git show --stat` 核对文件集合；`git log` 核对提交数；汇报 hash / subject / files / checks |
| FR-11 | **失败处理** | 中途失败报告现场；不自动 reset / amend / 改写历史 |
| FR-12 | **边界**：不推送、不改写历史、不 hunk 拆分 | 全程不出现 push / amend / rebase / reset / force / `git add -A` / `--no-verify` |
| FR-13 | **单主题调用** | 单主题时仍按同一消息格式与检查执行，不强行拆分 |

### 4.2 非功能需求

| 编号 | 需求 | 约束 |
| --- | --- | --- |
| NFR-1 | 纯提示词 | 无运行时依赖，不执行安装 |
| NFR-2 | 交互预算 | 计划确认 ≤1 轮；只在 staged 冲突、敏感 / 大文件、检查失败等歧义点追问 |
| NFR-3 | 可移植 | 先读取项目规范与检查命令，不硬编码本仓库命令 |
| NFR-4 | 安全 | 不擅自丢弃 staged 状态、不擅自改写历史、不推送 |
| NFR-5 | 可读性 | SKILL.md 只写行为要点；设计依据、测试映射与风险留在本文档 |
| NFR-6 | 跨 agent 兼容 | 不硬编码具体提问工具名；优先使用宿主结构化提问 / 选择工具，缺失时退回纯文本提问 |

## 5. 流程摘要

0 预检 → 1 分组与计划（默认确认）→ 2 逐主题提交（显式 add / 空提交守卫 / 快速检查 / hook）→ 3 收尾（完整测试 / 状态与提交核对 / 汇报）。

失败时停在原地并报告，不自动回滚或改写历史。

## 6. 提交信息示例

```text
feat(deep-research): 增加源码调研协议

- 阶段 1 识别源码调研，确认门列出源码获取计划
- 阶段 4 clone 到 sources/ 并固定完整 commit SHA
- 版本升至 0.4.0
```

```text
docs(repo): 清理文档版本沿革与失效记录

- 清理 ddgs-web-access、video-insight、md2pdf 文档中的版本沿革
- 修正测试集适用版本与失效路径
- 统一仓库规范与测试集的版本口径
```

## 8. 风险与开放问题

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | 纯提示词对 staged / secrets / 大文件的约束力有限 | 明确"最佳努力"；建议项目配置 hook / CI / secret scanning |
| R2 | 单文件多主题无法完全隔离 | 整文件归主主题并在 body 说明；高纯度需求由用户手动拆分 |
| R3 | hook 可能在提交前修改文件 | 重新暂存并重试；不自动 amend |
| R4 | 完整测试耗时 | 每个提交只跑快速项，批次结束跑完整测试 |
| R5 | 项目规范差异（语言、type、scope、长度） | 先读项目规范；无规范时用默认 Conventional Commits |
| R6 | 直接在默认分支提交 | skill 不强制分支策略；按项目规范执行，推送另行确认 |
| O1 | 是否支持非交互 patch 拆分 | 当前不做；若未来有可靠的非交互工具再评估 |
