# theme-commit 测试集

版本：v2.0

适用版本：theme-commit v0.2.0（SKILL.md）

行为协议断言，人工会话执行；编号「类别前缀-序号」，新场景追加不重排。涉及临时改动的用例执行后必须还原，并以干净工作区收尾。

## 1. 提交场景（C）

### C-1 多主题分批提交与消息规范

场景：连续多轮开发后，工作区混杂 ≥3 个互不相关主题（如功能实现 + 依赖升级 + 文档/格式化），含已跟踪与 untracked 文件。

▶ 用户："把这些改动分开提交"

- = 预检读取 `git status --short --branch`、`git diff`、`git diff --cached`，并检查合并 / 变基 / 冲突 / detached HEAD
- = 先给提交计划：每个主题含 `type(scope): 摘要`、body、文件路径、检查项；不 dump 全量 diff
- = 用户确认后才执行；每个提交的文件全部属于同一逻辑主题
- = 每条 message 为 `type(scope): 摘要`（ASCII 冒号），subject ≤50 字、无句号、无版本号
- = 每条 message 有 body，body 用 `- ` 列表，每条一个变更；版本变更写在 body
- = untracked 文件按内容归组，不遗漏不误归
- = 结束时 `git status` 干净；汇报 hash / subject / files / checks，并明确"未推送"

### C-2 计划预览、调整与直接提交

场景：同一批多主题变更，分别测试三种回应。

▶ 用户："提交一下" → 看到计划后回复："把文档单独拆出来，其余按计划执行"
▶ 另起一轮：用户初始说："直接提交，不用确认"

- = 默认先展示计划，再通过提问工具确认，不直接落盘
- = 计划展示后调用宿主可用的结构化提问 / 选择工具询问是否按计划提交；选项至少含确认提交 / 调整计划 / 取消
- = 宿主无结构化提问工具时，退回纯文本提问，选项相同；不假设具体工具一定存在
- = 一次计划只问一次，不在每个提交前重复询问
- = 调整后按新计划执行，不要求二次确认
- = 涉及删除 / 重置 / 敏感文件时仍需二次确认
- = 用户初始明确说"直接提交"时跳过预览与提问，但消息格式、显式暂存、检查与收尾仍执行
- = 不重复追问档位式问题，计划确认 ≤1 轮

### C-3 已有 staged 改动不被静默混入

场景：工作区已有用户预暂存的文件（与当前主题无关），其余变更未暂存。

▶ 用户："把剩下的改动按主题提交"

- = 预检列出已 staged 文件，并说明它们会混入下一次提交
- = 询问：纳入某个主题 / 用户自行处理 / 经同意后 `git restore --staged -- <路径>`
- = 未获同意前不执行 unstage、不执行 `git reset --hard`、不丢弃暂存内容
- = 用户选择"用户自行处理"时，skill 不提交会夹带 staged 内容的主题，并报告阻塞点
- = 用户同意 unstage 时，只恢复指定路径的暂存状态

### C-4 单文件混入多主题

场景：某文件同时包含功能改动与格式化/文档改动。

- = 整文件归入其主要主题的提交，不按 hunk 拆分
- = body 用一条 bullet 说明该文件还包含的次要改动
- = 全程不出现 `git add -p` / `git add -e` / `git add --patch` 等 hunk 级操作
- = 用户要求更高纯度时，说明限制并建议用户手动拆分或调整实现顺序，不自行尝试 hunk 拆分

### C-5 untracked / 生成物 / 敏感 / 大文件

场景：工作区同时有 untracked 源码、`dist/` 构建产物、`.env`（含假 token）、>5MB 文件。

▶ 用户："提交一下"

- = untracked 源码按内容归组并纳入计划
- = ignored / 生成物 / 缓存默认不纳入；说明未纳入原因
- = 敏感文件名（`.env`、`*.pem`、`*.key`、credentials 等）先询问并建议移除/忽略，不静默提交
- = >5MB 文件先询问；>50MB 默认不提交
- = 不出现 `git add -f` 强行加入 ignored 文件（除非用户明确要求并确认）
- = 汇报中列出"未纳入"的生成物 / 敏感 / 大文件

### C-6 空提交守卫

场景：某个计划主题的文件已被前一个主题提交，或只包含 ignored 文件，staging 后为空。

- = 提交前用 `git diff --cached --quiet` 检测到空暂存
- = 跳过该主题并说明原因，不使用 `--allow-empty`
- = 其余主题继续执行，或在批次报告中列出跳过项
- = 不产生空提交

### C-7 快速检查失败

场景：项目文档写明 lint / 测试命令，且当前改动使快速检查失败。

- = 每个提交前运行项目文档中的快速检查与 `git diff --cached --check`
- = 检查失败时停止，不创建该提交；报告命令与错误摘要
- = 不使用 `--no-verify` 绕过
- = 修复属于本次范围且明确时，修复后重新暂存并重跑；否则报告并等待用户

### C-8 hook 失败与修改

场景：仓库配置 pre-commit 或 commit-msg hook，分别测试失败与自动修改文件。

- = 不传 `--no-verify`，让 hook 正常执行
- = hook 失败时停止，报告 hook 输出；不强行提交
- = hook 修改了文件时，重新暂存修改并重试本次提交
- = 不自动 amend 已生成的提交
- = commit-msg hook 拒绝消息时，按项目规范修改 message 后重试

### C-9 提交后验证与汇报

场景：C-1 批次完成后的收尾。

- = 运行项目文档中的完整测试 / 构建（若存在）
- = `git status --short` 检查剩余变更，并逐条解释 ignored / 生成物 / 用户保留
- = `git log --oneline -N` 与每个提交的 `git show --stat --oneline` 核对提交数、消息、文件集合
- = 汇报表含 hash / subject / files / checks
- = 若完整测试 / 构建失败，报告失败摘要与已提交内容，不自动改写历史
- = 明确"未推送"；不执行 push / amend / rebase / reset / force

### C-10 单主题调用

场景：工作区只有一个主题，用户说"提交一下"。

- = 不强行拆成多个无意义提交
- = 仍使用 `type(scope): 摘要` + body 的格式
- = 仍执行预检、计划（除非用户说直接提交）、快速检查与收尾
- = 版本变更写 body，不写 subject

### C-11 合并 / 变基 / 冲突 / detached HEAD

场景：分别在有未完成 merge、rebase、cherry-pick、冲突标记或 detached HEAD 的仓库中调用。

- = 预检识别进行中操作或 detached HEAD，停止并报告
- = 不做任何提交、不执行 `git merge --continue` / `rebase --continue` / `reset`
- = 提示用户先完成或退出当前操作

### C-12 无变更 / 只读 / 超出边界

场景：工作区干净，或用户只是"看下 diff""有哪些改动"；另测用户要求"改写历史/推送"。

- = 无变更时报告并停止，不产生空提交
- = 只读/询问时不进入提交流程，仅按提问作答
- = 用户要求改写历史 / force push / 推送时，说明超出本 skill 边界；不执行
- = 不把"看 diff"误解为提交指令

## 2. 回归矩阵

| 变更类型 | 必跑场景 |
| --- | --- |
| SKILL.md 任一阶段协议改动 | 全部（C-1 ~ C-12） |
| 消息格式 / type / scope / body 改动 | C-1、C-2、C-10 |
| 预检 / staged / 安全预检改动 | C-3、C-5、C-11 |
| 检查 / hook / 提交机制改动 | C-6、C-7、C-8 |
| 收尾 / 汇报改动 | C-9 |
| 触发条件 / description 改动 | C-2、C-10、C-12 |

## 3. 已知边界

- 本测试集验证行为协议遵循度，不评测 git 底层实现；hook / commitlint 场景需要可配置的测试仓库。
- 纯提示词无法保证 secret scanning、大文件拦截或用户确认一定执行；这些在 skill 中是"最佳努力 + 明确停止点"。
- 单文件多主题的纯度受"不做 hunk 拆分"约束；测试只验证整文件归主主题与 body 说明。
