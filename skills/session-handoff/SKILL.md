# session-handoff：把会话打包成可粘贴的交接提示词

会话收尾时使用：通读全程，产出一段**自包含的交接提示词**——用户原样粘贴到新会话开头，接手的 Coding Agent 在无历史上下文的情况下恢复状态、制定计划、继续开发。

接手方一般已通过自动注入读到 AGENTS.md 等项目上下文，因此交接词不搬运项目基本面，只交付会话增量（见"面向 AGENTS.md 的取舍"）。

## 生成前核对

- 通读整个会话：任务目标、已完成的改动、关键决策、失败尝试、未决问题、下一步。
- **用命令核对事实，不凭记忆**：`git status`（分支、未提交变更）、`git diff --stat`（变更清单）、`git log --oneline -5`（提交锚点）；非 git 项目跳过此步。
- 会话与仓库均无从佐证的内容不编造；密钥、token、密码一律用 `<占位符>` 代替。

## 交接提示词骨架

按以下骨架成文：7 节必含 + 第 8 节条件保留（尖括号为提示占位，成文时替换为真实内容）：

```markdown
# 会话交接：<一句话概括任务>

## 1. 任务与目标
（要解决的需求 + 一句话验收标准；项目背景不展开——接手方会从 AGENTS.md 读到）

## 2. 当前进度
（已完成 / 进行中 / 未开始；一句话定位阶段，如"接口已通，前端未联调"；分支名与未提交变更）

## 3. 关键变更
（文件清单：路径 + 一句话说明；涉及函数 / 类名；报错原文照贴）

## 4. 关键决策与原因
（技术选型、约定、被否决的方案及原因）

## 5. 待办与下一步
（按优先级排列；每项写明预期产出与涉及文件）

## 6. 已知问题与风险
（未解决的 bug、阻塞点、开放问题；失败尝试写明试了什么、为什么失败）

## 7. 开工指引
（第一个明确动作，如"先运行 <命令> 确认环境，再读 <文件>"；附建议计划框架：先验证什么、再做什么、最后做什么）

## 8. 补充（AGENTS.md 未覆盖）
（仅在确有内容时保留本节：AGENTS.md 之外的环境变量、新模块位置、本会话新立的约定等；无内容整节省略）
```

## 面向 AGENTS.md 的取舍

- 项目背景、目录地图、构建 / 测试 / 运行命令、通用代码约定——AGENTS.md（或等价自动注入的上下文文件）已覆盖的，**不重复、不搬运**。
- 交接词只写三类内容：本会话的增量事实（改动、决策、进度）；与 AGENTS.md 的偏差与补充；接手方无处可查但必须知道的信息。
- 项目无 AGENTS.md（或已知新会话不会自动注入）时，把环境与运行方式、重要文件地图、约定与禁忌并入第 8 节补全——"能独立开工"的底线不因精简而失守。

## 写作要求

1. **只输出交接提示词本身**，放在一个 markdown 代码块内（便于整段复制）；块外不要有任何解释、总结或寒暄。
2. 以第二人称对下一个 Agent 说话（"你接手的是…""你的第一步是…"）。
3. 语言与本次会话保持一致。
4. 具体、可验证：真实文件路径、函数 / 类名、分支名、命令、版本号、报错原文。反例："修改了相关文件""优化了部分逻辑"；正例："`src/auth.py` 的 `login()` 新增 3 次指数退避重试（50ms 起）"。
5. 区分确定与不确定：未验证的结论标"（待验证）"，悬而未决的问题标"（未决）"。
6. 不得包含密钥、token、密码等敏感信息，一律用 `<占位符>` 代替。
7. 精炼打包，以"能立刻继续干活"为准：一般 400–1200 字；信息多时优先保留影响下一步行动的事实。
8. 本次会话失败过的尝试必须写明"试了什么、为什么失败"，防止接手方重蹈覆辙。
9. 必含节确实无内容时写"本会话未涉及"；第 8 节无内容时整节省略。

## 收尾核验

输出前自检——接手方带着（自动注入的）AGENTS.md + 这段文字，能否独立开工？不能则补齐缺失信息后再输出。
