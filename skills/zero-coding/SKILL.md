# zero-coding：从零到可用的个人项目

**核心信念**：Agent 能力越强，过多的文档越是束缚。只维护代码与 git 历史推导不出的信息。

**一条判断标准**：能从代码 + git 历史推导的 → 不写；表达意图、范围、约束、决策的 → 写。

## 分路

首次触发先判路，一句话告知所选路线怎么走（含硬门槛），用户可当场改判：

- **小活**：一个会话能做完（小工具、脚本、单页面）——对齐一轮 → 平台 Plan Mode（没有则 3~5 句方案）→ 直接实现。全程不建项目文档，仅在有不可逆选择时记 DECISIONS。
- **立项**：需要多会话的 MVP——走立项流程（SPEC → 骨架 → 逐片实现 → 收敛收尾）。

判据是会话容量：当前上下文窗口装得下从想法到交付的全过程，就走小活路线。

## 对齐（两路共用）

目标：与用户达成共享理解——待定项问尽，没有任何决策被默默假设。

**怎么问**

- 把待定项按依赖分层：每轮一次问完“前提已定、现在就能问”的那批，答完再进下一轮。
- 每题编号并附推荐答案：

  ❓ **Q1** - **<标题>**：<问题正文，可含选项>
  ➡️ 推荐：<答案 + 一句理由>

**通道分工**

- **事实 → 自查**：环境、工具、资料凡能自己调研的绝不问用户，必要时派子 Agent；调研未返回只阻塞它的下游，其余照常推进。
- **决策 → 问人**：有明确选项、能口头裁决的，摆给用户并等待；Agent 只推荐、不拍板。
- **说不清的 → 做原型**：想不清楚、口头裁决不了的实现问题，做一次性原型给用户看——最小可运行即可，不抛光、不写测试、默认不持久化；明确标注弃用，结论记入 DECISIONS，本体删除。用户对原型的反应就是裁决。

**借力平台**：所在平台有 Plan Mode 时，探索与方案梳理借其只读模式进行，产出的计划即 SPEC / 实现方案素材。

## 立项流程

### SPEC

对齐结束后，把全部已定决策综合为 SPEC 交用户确认。**硬门槛：SPEC 未获用户明确确认前，不写任何产品代码（原型除外）。**

```
# SPEC

## 问题
（为谁解决什么问题）

## 走通路径
（一句话：用户从启动到拿到结果全程怎样走完；MVP 交付判据 = 这条路全程可演示）

## 切片
1. <切片一>：端到端走通 <输入 → 输出>；验证方式：<一句话>
2. <切片二>：……
（每片穿过存储 / 处理 / 界面各层的最窄一条，独立可验证、一片一提交；
禁止按层横切；实现方式未定的片标注“开工前先做原型”）

## 非目标
（明确不做什么）
```

范围变更 = 重写对应节，按“新需求从一开始就是这样”书写，不追加变更说明——SPEC 是文档集中唯一可改写的文件。

### 骨架

1. 初始化代码骨架至“可运行空壳”（hello-world 级）。
2. 写 AGENTS.md——每条命令必须真实执行过；README 写最小版（怎么跑）。
3. 本阶段全部选型逐条记入 DECISIONS.md。

### 逐片实现

迭代循环：按 SPEC 切片清单取下一片 → 实现 → 测试绿 → 一片一提交。

- 常规切片（改法显然、可逆）直接做，不打断节奏。
- 实现方式不显然的切片动工前先对齐：所在平台有 Plan Mode 就走 Plan Mode，没有则给 3~5 句实现方案（思路、涉及面、取舍点）交用户确认；讲不清楚就退回做原型。

文档纪律：

- 不可逆选型拍板 → 当场追加 DECISIONS（Agent 起草，用户只确认理由）。
- Agent 犯重复错误 → 纠正写入 AGENTS.md，保持 <100 行。
- 范围变化 → 重写 SPEC 对应节；永久放弃同时记一条 Decision。

### 收敛收尾（MVP 交付）

1. 对照 SPEC 走通路径逐片核验，缺的补完——以交付判据（全程可演示）为准，而非任务清单勾完为准。
2. SPEC 删除（或按用户意愿归档）；README 完善至一屏。
3. DECISIONS 与 AGENTS 继续服役，进入下一个循环。

## 文档集（3 个，不增不减）

| 文件 | 读者 | 一句话定位 | 生命周期 |
| --- | --- | --- | --- |
| docs/SPEC.md | 用户 + Agent | 范围契约，只综合已定决策 | MVP 交付后删除 |
| docs/DECISIONS.md | Agent | 轻量 ADR，条目一行式，只追加 | 永久 |
| AGENTS.md | Agent | 会话级上下文，保持克制 | 持续维护 |

- DECISIONS 条目：`D1 · 2026-09-13 · 存储用 SQLite · 为什么：单机自用，零运维优先于扩展性`。决策被推翻时追加新条目并注明“取代 D1”，不删旧条目；重构或选型前必读，与生效条目冲突的改动先向用户提出。
- AGENTS.md 写构建 / 测试 / lint 命令、目录速览、硬约束，只在 Agent 犯**重复**错误时追加纠正；模板建议里保留一句书写纪律：产物按现状书写，演进过程交给提交说明与 DECISIONS。
- README.md 是常规惯例（是什么、怎么跑，一屏以内），骨架期写最小版自然长成，收尾时完善，不另立仪式。

## 冲突裁决

用户当面指示 > DECISIONS > 其余文档。代码与文档冲突时，以 DECISIONS 为准提醒用户，并修正过时文档。
