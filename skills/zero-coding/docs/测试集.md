## 1. 工作流场景（Z）

### Z-1 首轮判路并告知

场景：空目录会话中，用户口述一个新想法。

▶ 用户：“我想做个读书笔记自动整理工具”

- = 首次触发先判路（小活 / 立项），一句话告知所选路线怎么走与硬门槛（立项路线含“SPEC 确认前不写产品代码”）
- = 判路附一句理由，判据是会话容量（当前上下文窗口能否装下从想法到交付的全过程）
- = 用户当场改判时按新路线走，不坚持原判断
- = 想法在会话中自由讨论，围绕想法不做技术判断以外的限制
- = 判为小活前不创建任何项目文档；判为立项也仅在对齐结束后才落 SPEC

### Z-3 对齐按层逐轮（两路共用）

场景：分路后进入对齐，与用户逼近共享理解。

- = 把待定项按依赖分层，每轮一次问完“前提已定、现在就能问”的那批，答完再进下一轮
- = 每个问题带编号与推荐答案（❓ Qn + ➡️ 推荐），等回答再进下一轮
- = 能自行调研的事实（环境、工具、资料）绝不问用户，必要时派子 Agent；调研未返回只阻塞其下游，其余照常推进
- = 决策留给用户：Agent 只推荐不拍板
- = 想不清楚、口头裁决不了的实现问题走原型通道（见 Z-13），不猜、不默默假设
- = 待定项问尽、无默默假设后，立项路线把全部已定决策综合为 SPEC 草案交用户确认；小活路线把结论整理为 Plan Mode 计划或 3~5 句方案交用户确认

### Z-4 SPEC 未确认不写产品代码

场景：立项路线对齐结束、SPEC 草案尚未获用户明确确认。

- = 不写任何产品代码（一次性原型除外）
- = 用户确认 SPEC 后才进入骨架

### Z-5 骨架可运行（立项）

场景：SPEC 已确认。

- = 初始化代码骨架至“可运行空壳”（hello-world 级）
- = AGENTS.md 中每条命令都真实执行过才写入，写完逐条验证
- = README 只写最小版（怎么跑）
- = 本阶段全部选型逐条记入 DECISIONS.md（一行式）

### Z-6 文档纪律（3 个，不增不减）

场景：立项后的开发与维护全程。

- = 持久文档只有 docs/SPEC.md、docs/DECISIONS.md、AGENTS.md 三个，能从代码 + git 推导的不写
- = 不可逆选型拍板 → 当场追加 DECISIONS（Agent 起草、用户只确认理由）
- = 决策被推翻时追加新条目并注明“取代 Dn”，不删不改旧条目
- = 与生效决策冲突的改动先向用户提出，不擅自更改
- = Agent 犯重复错误才把纠正追加进 AGENTS.md，保持 <100 行
- = 范围变化 → 重写 SPEC 对应节；永久放弃同时追加一条 Decision
- = AGENTS.md 模板建议保留一句书写纪律：产物按现状书写，演进过程交给提交说明与 DECISIONS

### Z-7 收敛收尾（MVP 交付）

场景：MVP 交付收尾。

- = 对照 SPEC 走通路径逐片核验，缺的补完——以交付判据（全程可演示）为准，而非任务清单勾完为准
- = SPEC 删除（或按用户意愿归档）
- = README 完善至一屏
- = DECISIONS 与 AGENTS 继续服役，进入下一个循环

### Z-8 冲突裁决

场景：开发中出现代码与文档、或文档间的不一致。

- = 用户当面指示 > DECISIONS > 其余文档
- = 代码与文档冲突 → 以 DECISIONS 为准提醒用户，并修正过时文档

### Z-9 反向不触发

场景：用户在已有成熟文档体系与开发规范的项目里求助，或只是临时提问、并不打算立项。

▶ 用户（在既有项目内）：“帮我看下这个函数为什么慢”

- = 不启动 zero-coding 工作流，不创建 SPEC / DECISIONS 等文件，仅按提问作答

### Z-12 MVP 范围格式（SPEC 草案）

场景：立项路线对齐结束，整理 SPEC 草案交用户确认。

- = 走通路径节一句话：用户从启动到拿到结果全程怎样走完，交付判据 = 这条路全程可演示
- = 切片节列垂直切片：每片从输入到输出端到端走通、独立可验证、一片一提交，附一句验证方式
- = 禁止按层横切的拆法（如“先做完全部数据层再做全部界面”）
- = 实现方式仍未定的片标注“开工前先做原型”，不算被默默假设

### Z-13 原型通道（说不清的做原型）

场景：对齐或开发中遇到想不清楚、口头裁决不了实现方式的问题（需求不常见、不稳定、不典型或较复杂）。

- = 不猜、不默默假设、不自行发挥：要么问用户，要么做一次性原型给用户看
- = 一个原型只回答一个问题，问题决定原型的形状；最小可运行即可——不抛光、不写测试、不抽象、默认不持久化
- = 原型明确标注弃用：不并入产品代码、不搭全局结构、不预留演进接口
- = 结论记入 DECISIONS，原型本体删除或另行存档；用户对原型的反应就是裁决
- = SPEC 确认前的原型不算产品代码（不违反硬门槛），但不得以原型名义实质开工

### Z-14 实现方式不显然的切片先对齐（委托平台）

场景：逐片实现中取到实现方式不显然的切片。

- = 动工前先对齐：所在平台有 Plan Mode 就走 Plan Mode，没有则给 3~5 句实现方案（思路、涉及面、取舍点）交用户确认，确认后才实现
- = 实现方案讲不清楚 → 退回做原型，不硬写
- = 切片带“开工前先做原型”标注 → 必触发对齐
- = 触发判别：多种可行走向 / 非常规做法 / 引入不可逆选择，任一命中即对齐
- = 改法显然、可逆的常规切片直接做，不额外打断用户

### Z-15 小活短路

场景：判路为小活（一个会话能做完的小工具、脚本、单页面）。

- = 对齐一轮后直接走平台 Plan Mode（没有则 3~5 句方案）交用户确认，然后实现
- = 全程不创建 SPEC / DECISIONS / AGENTS 等项目文档
- = 仅在出现不可逆选择（选型、外部服务、数据格式）时记 DECISIONS，且条目同样一行式、只追加
- = 收尾只验证交付可用，无 SPEC 收敛、README 完善等立项收尾动作
