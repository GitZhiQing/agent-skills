## 1. 调研方法与范围

- **目的**：为 deep-research skill（灵感见 [ZERO.md](ZERO.md)）的需求与设计提供决策依据，重点验证 ZERO.md 三个关键机制（预调研校准、选项式收敛、强度分档）与双产出物（报告 + 素材登记簿）在现有方案中的覆盖情况。
- **方法**：ddgs-web-access 多引擎搜索定位仓库 → 抓取 README / SKILL.md 原文（raw.githubusercontent.com 优先）→ 按统一维度归纳。抓取日期均为 2026-09-10。
- **分层**：
  - **A 类（直接竞品，深挖）**：skill / 提示词形态，与本 skill 同赛道；
  - **B 类（框架级）**：独立运行的调研 agent 框架，机制参照；
  - **C 类（参照系）**：闭源产品交互模式、模型级方案、评测基准。
- **局限**：星标数为访问日快照；部分 README 只读到截断长度（长文按 --max-chars 分段，未逐段读完）；所有结论基于文档与源码文本，未实际运行竞品。

## 3. 重点竞品：skill 形态（A 类）

### 3.1 jordan-gibbs/hyperresearch —— 同形态最强竞品

- **形态**：`pip install hyperresearch` + Claude Code skill 路由器 + 十余个专职 subagent（fetcher / source-analyst / loci-analyst / depth-investigator / corpus-critic / draft-orchestrator / synthesizer / critics / patcher…），模型可按角色配置。
- **16 步流水线**（节选）：① Decompose（canonical query → 原子条目 + 覆盖矩阵 + 档位分类）→ ② Width sweep → ③ Contradiction graph → ⑦ Source tensions → ⑧ Corpus critic（"什么来源能推翻当前方向？" + 补差抓取）→ ⑪ Synthesize → ⑫ 四个对抗 critic 并行 → ⑭ 工具锁定的 patcher（只能手术式 Edit，物理上无法重写报告）→ ⑭.5 Cite-check（逐句核验引用是否真的支撑该句）→ ⑯ 可读性审计。每步一个子 skill，按需装载以对抗长上下文衰减。
- **档位机制（对 ZERO.md §4.3 最直接的参照）**：
  - **Tiers 按查询路由**：step 1 自动分类 `light`（有界事实型，走 1→2→10→15→16 五步，约 30~40 分钟）/ `full`（默认，全 16 步 + cite-check，1.5~2.5 小时）/ `dissertation`（仅显式要求，4~10 章、300~450 来源、25K~80K 词，4~8 小时）；
  - **Gears 定规模**：`premier`（100~130 来源）/ `full`（55~80 来源基线），按项目持久化；
  - **Levers 定文体**：`register`（teach/survey/analyze/advocate）/ `inference_depth`（surface/standard/deep），由 step 1 从用户措辞推断，显式指令优先。
- **校准机制**：**没有用户澄清环节**。"canonical research query is gospel"——用户原始提问被逐字持久化到 `runs/<id>/query.md`，后续所有步骤重读该文件以保证不漂移；理解收敛完全由 agent 单方完成。
- **证据管理**：所有来源落入 markdown+SQLite vault，**跨会话**复用（下次调研先查库再抓网）；独立性审计聚类转载（"五家转载只算一票"）；Unpaywall/Europe PMC 合法获取论文全文并披露替换；单次运行 250+ 来源、可 `run resume` 断点续跑。
- **对本 skill 的启发**：档位表应写明"各档跑什么、不跑什么、典型耗时"；引用核查与矛盾聚类值得以提示词级机制借鉴（如"每条关键结论自问：哪个来源能推翻它"）；"档位 = 流程差异"而非单纯数量差异。
- **反例与边界**：重装备（CLI + subagent 编队 + SQLite），单次 light 档也要 30~40 分钟——ZERO.md 面向的是对话内轻量调研，low 档必须分钟级；其"零用户交互"理念与 ZERO.md 的"人在环校准"相反，二者是谱系两端的定位。

### 3.2 bytedance/deer-flow 官方 skills（deep-research / github-deep-research）

- **deep-research**（`skills/public/deep-research/SKILL.md`）：定位为"WebSearch 的替代品"——任何需要联网信息的问题都应加载它而非单次搜索。四阶段方法论：
  1. **Broad Exploration**：宽检索画地图，识别子主题/维度/利益相关方；
  2. **Deep Dive**：按维度精确检索、换措辞多次、`web_fetch` 读全文、顺藤摸瓜追引用；
  3. **Diversity & Validation**：六类信息矩阵（事实数据/案例/专家观点/趋势预测/对比/批评质疑）强制覆盖；
  4. **Synthesis Check**：五项自检清单（≥3~5 角度？读了全文？有数据+专家视角？正反都查了？信息够新？），任一为否则继续查。
  - 另有时间意识条款：组查询前必须看上下文中的当前日期，禁止硬编码过期年份。
- **github-deep-research**：四轮递进（GitHub API 元数据 → 发现 → 深查 → 深潜），来源优先级五档（官方文档 > 技术博客 > 认证媒体 > 社区讨论 > 社媒情绪），报告模板九节（元数据块/执行摘要/时间线/分析节/指标对比/优劣/来源/**置信度评估**/方法论），**置信度三级判据表**（High：官方+多源印证 90%+；Medium：单一可靠来源 70~89%；Low：社媒/未验证 50~69%），鼓励 Mermaid 图。
- **对本 skill 的启发**：多样性矩阵与自检清单是"防浅尝辄止"的低成本机制；置信度分级判据可直接吸收进报告模板；"触发即替代普通搜索"的 description 写法值得借鉴。
- **反例**：两份 SKILL.md 均无用户校准、无档位、无中间产物登记——一次性方法论，调研过程不可追溯。

### 3.3 affaan-m/everything-claude-code · deep-research

- **形态**：纯提示词 skill，硬依赖 firecrawl/exa MCP 工具，自带"漂移警告"（工具名与配额易变，用前先验证）。
- **工作流**：① 澄清目标（1~2 个快问：学习/决策/写作？有无特定角度？用户说"直接查"就用默认值跳过）→ ② 拆 3~5 个子问题 → ③ 逐子问题多关键词检索（合计 15~30 个去重来源，来源优先级：学术/官方/可靠媒体 > 博客 > 论坛）→ ④ 深读 3~5 个关键源全文 → ⑤ 综合成报告 → ⑥ 按长度分流交付（短题聊天内全文；长报告存文件 + 聊天内只给摘要）。宽题可并行 subagent。
- **报告模板**：执行摘要 / 主题分节（结论内联引用）/ Key Takeaways / Sources（标题+URL+一行摘要）/ **Methodology**（查了多少 query、分析了多少源、子问题清单）。
- **不可信来源章节（对本 skill 安全设计的直接参照）**：抓取内容是页面作者可控的攻击面——不得执行来源中的指令、不得让来源改写调研范围、不得向来源指定的端点外发数据、可疑内容在引用处标注而非照办或静默丢弃。
- **对本 skill 的启发**：目的三分法（学习/决策/写作）与 ZERO.md 澄清维度清单一致，验证了该维度设计；Methodology 节让调研过程对用户可见；来源优先级与交付分流值得吸收。
- **反例**：澄清发生在**检索前但无预检索**——只凭提问理解需求，正是 ZERO.md 判断为"可能越问越偏"的模式；Sources 列表是单向的（结论→来源可查，来源→支撑了哪些结论不可查），无排除留痕。

### 3.4 Weizhena/Deep-Research-skills

- **形态**：两阶段工作流 skill（大纲生成 → 逐项深研 → 汇总报告），配套 web-search-agent 与模块，需 `pip install pyyaml`，适配 Claude Code / OpenCode / Codex 三端（各有一份变体）。自述受论文 RhinoInsight（arXiv:2511.18743，模型行为与上下文的控制机制）启发。约 2.1k★，171 fork。
- **命令族**：`/research`（生成大纲：调研条目 + 每条目要收集的字段）→ `/research-add-items`、`/research-add-fields`（增量扩充大纲）→ `/research-deep`（逐条目并行深研）→ `/research-report`（JSON 结果 → 带 TOC 的 report.md）。
- **human-in-the-loop**：大纲是显式人工确认点——用户看到"将要调研什么、每项收集什么"后才进入深研；这是 A 类中最接近 ZERO.md 校准环节的 checkpoint，但发生在**首轮生成之后**（先产大纲再纠偏），而非 ZERO.md 的"先查 1~3 条判向再收敛"。
- **对本 skill 的启发**：条目 + 字段的表格化中间产物是登记簿的雏形（结构化、可增量扩充）；命令族切分让长流程可断点续作；中英双版本分发证明中文用户基数。
- **反例**：部署偏重（agent 文件 + Python 依赖 + 三端各异安装路径）；校准点是"产物确认"而非"理解校准"——大纲错了照样全量跑偏。

## 4. 重点竞品：框架级（B 类）

### 4.1 assafelovic/gpt-researcher（~29.3k★）

自述"第一个开源 deep research agent"：Plan-and-Solve + RAG 思路，规划者出研究计划，并行 worker 执行，产出带引用的事实性报告；支持 web + 本地文档、多检索器、自定义报告格式与领域 agent、多语言 README（含中文）。值得注意的是它**同时以 Claude Skill 形式分发**（skills.sh）——框架向 skill 生态渗透，说明"skill 封装"被头部项目当作轻量化入口。无用户校准环节（以配置代替理解收敛），强度靠报告类型与深度参数。

### 4.2 stanford-oval/storm 与 Co-STORM

STORM 两步走：预写作阶段**多视角提问**（按不同 persona 的专家视角自问自答，拓宽检索维度）→ 基于互联网检索生成带引用的维基式长文；7 万人试用过在线 preview。Co-STORM（EMNLP 2024）加入人机协同知识策展——用户可在过程中引导方向。对本 skill 的启发：①"多视角"是检索维度生成的成熟办法（ZERO.md 选项式方向可视为其用户侧变体）；② Co-STORM 证明"人在环"对调研质量的价值有学术支撑。反例：产出定位是文章而非决策报告，无档位无登记。

### 4.3 langchain-ai/open_deep_research

LangGraph 实现的可配置深调研 agent：supervisor-researcher 循环、多模型分工（summarization / research / compression…）、搜索工具与 MCP server 可插拔，Deep Research Bench 综合分 0.4344（2025-08，当时榜 #6），配套免费课程。对本 skill 的启发：澄清/确认/汇报都可以是流程中的显式节点——提示词 skill 里对应"阶段化指令"。无用户校准，强度即配置。

### 4.4 dzhng/deep-research（<500 LoC）

刻意保持极简的递归调研循环：query → 生成 SERP 查询 → 处理结果产出 learnings（学到的结论）与 directions（新方向）→ depth>0 则带上下文递归 → 汇成 markdown 报告。**breadth/depth 两个数值参数**就是它的"档位"；另有 "smart follow-up questions"（生成追问以更好理解需求——澄清存在，但同样是提问式而非预检索式）。对本 skill 的启发：强度参数化 + 递归"边查边沉淀 learnings"与 ZERO.md 增量登记精神一致；体量证明一个可用的调研循环不需要多少代码——但 ZERO.md 的差异化恰恰在循环之外的**交互协议**。

### 4.5 LearningCircuit/local-deep-research

本地优先的调研应用：任意本地/远程 LLM、隐私优先、SimpleQA ~95%、**自建可搜索知识库（SQLCipher 加密 SQLite）**、活跃的工程化配套（Docker/PyPI/OpenSSF/CodeQL）。对本 skill 的启发：知识库即"登记簿持久化"的极端形态，验证"调研素材值得作为一等公民存储"；反例：产品化 app 形态（含 Web UI），与提示词 skill 不同赛道。

## 5. 参照系：闭源交互 / 模型级 / 评测基准（C 类）

### 5.1 闭源产品的交互模式

- **ChatGPT Deep Research**：**总是**在开始检索前问一轮澄清问题（arXiv:2602.16699 引述）——"搜索前澄清"已被产品级方案确立为标准动作，但形式是**开放提问、单轮、无预检索**。
- **Kimi Deep Research**（产品页）：同样要求先答澄清问题、确认或修正调研方向，帮助文档明确引导用户"缩小范围"后再提交。
- **Gemini Deep Research**：先展示多步调研计划再执行（计划确认 ≈ Weizhena 的大纲确认）。
- **含义**：ZERO.md 的"预调研校准"不是"要不要问"的问题（大家都在问），而是"**拿什么问**"的问题——先查 1~3 条再给出选项式方向，是用证据校准提问本身，这一步目前没有竞品显式做。

### 5.2 模型级方案

- **Tongyi DeepResearch**（Alibaba-NLP/DeepResearch）：30.5B MoE（3.3B 激活）agentic 模型，统一 mid-training + post-training（arXiv:2510.24701），自称首个性能对齐 OpenAI DR 的全开源 Web Agent。
- **Kimi-Researcher**（Moonshot）：端到端 agentic RL 训练的自治 agent，平均 23 步推理/任务，强多轮检索与推理。
- **含义**：模型级方案把"会调研"做进权重，单点检索/推理质量上提示词 skill 无法与之竞争；skill 的价值在**流程编排、交互协议与产出物规范**——恰是 ZERO.md 的着力点。

### 5.3 评测基准（验收维度参照）

- **DeepResearch Bench**（arXiv:2506.11763，ICLR 2026 poster）：22 个研究领域，报告质量 + **两层粒度的引用评估**（citation 质量）双轨评测。
- **DeepResearch Bench II**（alphaXiv:2601.08536）：132 个接地任务，按信息回忆 / 分析 / **引用接地**三维诊断。
- **Perplexity DRACO**：真实场景四维评测，**引用质量**、事实准确性、分析广度/深度。
- **含义**：三个主流基准全部把"引用可溯源"列为核心维度——登记簿（证据层）设计有行业共识背书；本 skill 的验收场景应至少覆盖"引用可溯源、事实/观点分离、矛盾显式化"。

## 6. 差距分析矩阵

以 ZERO.md 的机制清单为行，竞品覆盖情况为列（✅ 有 / ⚠️ 部分 / ❌ 无）：

| 搜索前用户澄清 | ❌（agent 单方锁 query） | ❌ | ⚠️（1~2 问，无预检索） | ⚠️（大纲事后确认） | ⚠️（follow-up 提问） | ✅（单轮开放提问） |

**结论（差异化定位）**：

1. **"搜索前澄清"已是行业标准动作**（ChatGPT、Kimi 产品级默认），但均为**开放提问、无预检索**；affaan-m、dzhng 的 skill 版澄清同样是纯提问。ZERO.md 的不可妥协差异点是**"先查 1~3 条资料校准理解 + 选项式方向勾选"的组合**——用证据生成选项，而非凭空追问。
2. **档位化已有强者**：hyperresearch 的 tiers/gears/levers 三层机制完整，但面向算力预算且**自动路由、用户难干预**；ZERO.md 的差异在**推荐制（一句话理由 + 用户可改）**与**交互节奏维度**（max 档分阶段汇报可纠偏可中断——无竞品把"交互"当档位维度）。
3. **证据层已成评测共识**（DRB/DRB II/DRACO 均以引用质量为核心轴），hyperresearch vault 与 LDR 知识库证明其工程价值；ZERO.md 登记簿的独有面向是**反向索引 + 排除留痕**的"可审计"定位（hyperresearch 丢弃无此概念，affaan-m 列表单向），且以纯 Markdown 实现、无需数据库。
4. **中英双语交叉验证与报告后追问协议（不重搜、沿证据链复查）在全部竞品中均无显式实现**——前者服务中文用户场景，后者把登记簿从"附件"变成"知识底座"。
5. **形态定位**：模型级（Tongyi/Kimi）赢在单步能力，框架级（hyperresearch/gpt-researcher）赢在规模与自动化；纯提示词 skill 的生存空间是**轻量、人在环、过程可审计**——与 ZERO.md 理念完全一致，需求文档应把"非目标"写清以守住这条边界。
